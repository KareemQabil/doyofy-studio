# التنفيذ والمراجعة والتشغيل

## نطاق هذه الدفعة

نقل مصدر المشروع والأصول والتخطيط إلى GitHub. لم تُنفذ الميزات التالية، ولم تُغير قاعدة بيانات أو إعدادات نشر الموقع. تقديرات التعقيد أدناه نسبية: S تغيير محدود، M يمر بعدة مكونات، L يغير عقد بيانات أو تكاملًا. ليست مواعيد تسليم مضمونة.

يمكن تطوير مكونات الواجهة وعقد البيانات كل منهما في نطاقه بعد حسم المعنى المشترك. لا تتأخر تجربة cross-device إلى آخر يوم: يبدأ proof صغير لـP11 بعد P02 وقبل الاعتماد على أي مشاركة إنتاجية، ثم تُمدد عقوده مع الميزات الجديدة. لا يلزم أن تنتهي كل الزخارف لاكتشاف أن البيانات لا تتشارك.

## ماذا نؤجل صراحة؟

- محفظة داخلية، تقسيم تحصيل، refunds، ودفع متتبع: حتى يُحدد البلد والمستفيد والمزود وسبب عدم كفاية الروابط.
- marketplace وحجوزات قاعات/موردين: المتحدث لم يحدد هذه الخدمات أصلًا؛ تعريف مستقل قبل تقديرها.
- auto-seating، محرر قاعة هندسي، وشطر عائلة بين الطاولات: طلب مختلف عن نقل party الموجودة.
- form builder عام متعدد أنواع الأسئلة: وحدتا طعام وهدايا كافيتان للطلب الحالي.
- توسيع الثيمات أو rewrite للمحرك: الإصلاح والتوحيد أولًا، ثم تقييم الحاجة.
- ظهور أزرار كاميرا/إرسال حقيقي قبل ربطها: تبقى المحاكاة معنونة حتى تنفذ الوظيفة.

## نقاط العرض على المالك

| checkpoint | ما يُعرض | القرار المطلوب |
| --- | --- | --- |
| C1 — سلوك ثابت | اختيار مناسبة + sheet + RSVP fail/retry | هل الحركة مفهومة وتخدم الفعل؟ |
| C2 — واجهة عمل واحدة | guests/table/reception على هاتف وديسكتوب | اتساق الهوية، كثافة المعلومات، quick actions |
| C3 — الطعام | عائلة من 4 + تفضيلات + ملاحظة قيد + تقرير/نقل طاولة | هل نحتاج أسماء كل مرافق أم الكميات تكفي؟ |
| C4 — الهدايا | حاضر ومعتذر والهدايا off/on ورابط خارجي | هل هذا يحقق الحاجة أم يتطلب دفعًا متتبعًا؟ |
| C5 — إغلاق | رحلة حقيقية عبر جهازين + قياسات وأصول | قبول النطاق المنفذ وتحديد ما بقي تجريبيًا |

كل checkpoint يعرض رحلة قصيرة كاملة، لا شاشة منعزلة تحتاج تخيل الربط. القرارات الروتينية عن المسافات والأيقونات تُحل داخل النظام المعتمد، ولا تتطلب تعطيل كل دفعة بسؤال جديد.

## المخاطر العملية وكيف نكشفها مبكرًا

| الخطر | الأثر | الكشف/التخفيف |
| --- | --- | --- |
| shared gesture يصلح سطحًا ويكسر آخر | أعطال واسعة | child-start وcancel/scroll/control matrix على جميع المستهلكين |
| سياسة الطعام تتغير أثناء الرد | إجابة على اختيار لم يعد موجودًا | revision conflict يحافظ على الصحيح ويطلب مراجعة المتغير |
| pending request يعاد إرساله | عدّ أو رسائل أو معاملات مكررة | idempotency واختبار timeout-after-write |
| unmatched response يُحسب مع party بعد المطابقة | تقارير مضللة | canonical source + separate provisional totals |
| يدوي وprovider status لهما الرسم نفسه | ثقة زائفة بالإرسال | source label وإثبات الحالة في contract |
| UI تعتمد hover أو drag | الهاتف لا يكمل المهمة | touch affordances وأزرار بديلة ومراجعة جهاز فعلي |
| التصميم يخفي الفورم بالكيبورد | تعطل RSVP/editor | visualViewport وfocus/safe-area/landscape |
| إضافة تقارير تكشف diet notes أو هواتف | وصول أكبر من الغرض | selectors/roles/exports محدودة واختبارات deny |
| GIF/3D/banner كبير في كل route | تكلفة تنزيل/تفاعل أكبر | route/media lazy loading وقياس المسار نفسه قبل/بعد |
| محاكاة تُفهم كخدمة فعلية | دعم وشكاوى وفشل رحلة | demo/preview/live boundaries في النص والعقد |

## القياس دون اختراع نتائج

نجمع baseline أولًا؛ لا توجد الآن أرقام موثقة عن زمن الإنشاء أو conversion أو FPS على الأجهزة. بعد كل تغيير نقارن المهمة نفسها على نفس الجهاز والبيانات.

| السؤال | المقياس المقترح | ما لا نسجله |
| --- | --- | --- |
| هل قللنا القرارات؟ | زمن الوصول إلى أول معاينة، رجوع الخطوات، مرات فتح اختيار القالب | نص الدعوة أو أسماء أصحابها |
| هل المشاركة أسهل؟ | عدد الخطوات لفتح واتساب، توقف/استكمال queue، فشل أرقام | محتوى الرسالة والهواتف في analytics |
| هل RSVP موثوق؟ | submit success/error/retry، زمن الحفظ، duplicate prevention | الملاحظات الحرة والقيود الغذائية |
| هل الطعام واضح؟ | أخطاء مجموع الوجبات، غير المحدد، edits، اختلاف الشاشة/التصدير | بيانات حساسية فردية خارج التشغيل |
| هل الهدايا مطلوبة؟ | تفعيل المضيف، فتح القسم والرابط، طلبات تتبع من المستخدمين | افتراض الدفع من click أو مبالغ وهمية |
| هل أضفنا عبئًا؟ | actual transfer وLCP/INP/CLS وlong tasks وFPS عند الحاجة | لا نطلق tracking خارجيًا في هذه الدفعة |

قياسات الاستخدام المقترحة لا تفعّل telemetry أو vendor تلقائيًا. سجل التشغيل يكتفي بالcodes/correlation وتعدادات منضبطة، مع إخفاء القيم الحساسة.

## القيمة التجارية والحدود

المنتج الأساسي القابل للاستخدام هو دعوة جميلة + مشاركة واضحة + ردود موثوقة + تشغيل ضيوف. الطعام يزيد قيمة المناسبات المنظمة، والهدايا تزيد التعبير والارتباط، لكن لا يجب أن تجعل الحضور عملية شراء.

تكلفة provider للرسائل، الصور، تخزين البيانات، وتشغيل المدفوعات تختلف عن تكلفة تطوير الواجهة. لا نفترض أن عمولة الهدايا هي نموذج الربح، ولا نحدد سعرًا أو مزودًا دون قرار منتج وسوق. تُقاس الحاجة أولًا؛ feature لا يستخدمها المضيف لا ينبغي أن تثقل كل ضيف.

## إصدار وعودة

feature flags لكل وحدة جديدة، off للمناسبات القديمة، وschema additions متوافقة. release notes تسمي ما هو live وما هو demo. rollback يُوقف ظهور الوحدة الجديدة دون حذف إجاباتها. لا تُجرى migration تدميرية لتسهيل تغيير UI.

أول PR فعلي يبدأ من branch منفصل مبني على import + docs، ويترك main نسخة قابلة للبناء. لا تشغيل لقواعد بيانات أو مزودين أو نشر Vercel ضمن مجرد اعتماد هذه الخطة.
