# البيانات والخدمات — عقد مقترح قبل التنفيذ

هذه مواصفة تصميم تقني وليست migration مطبقة. القيم والأسماء قابلة للتعديل أثناء التنفيذ؛ المعاني والثوابت أهم من مطابقة هذه الأسماء حرفيًا.

## ما يوجد الآن

`InvitationParty` تمثل دعوة عائلة، و`confirmedPartySize` عدد أشخاص، و`tableId` يوزع العائلة كوحدة. يوجد `companionNames[]` اختياري وملاحظة ضيف؛ لا يوجد نموذج وجبات أو هدايا. `RSVPResponse` قد يكون بلا party عند الرد من الرابط العام. `InvitationDesign` لديه draft/published، لكن `Event.settings` لا يملك دورة نشر مستقلة.

كل خدمات التشغيل الحالية تصدر من mock محلي. توجد remote adapters وSQL مسبقة الإعداد؛ وجودها واختبار mocked-fetch لا يثبتان أن خادم إنتاج مفعل أو آمن لكل إضافة جديدة.

## حدود الكيانات

| الكيان | مسؤولية واحدة | ما لا يدخل فيه |
| --- | --- | --- |
| Event | المناسبة والموعد والمكان والسماحية | وصف الشكل والخامات |
| InvitationDesign | وجه البطاقة والمشهد والمحتوى المرئي | بيانات مالية أو إجابات الضيوف |
| GuestExperiencePolicy | أسئلة الطعام والهدايا وما يظهر للضيف | إجابات الضيف أو قبول الدفع |
| Party | الدعوة والعائلة والحضور والطاولة | اعتبار العائلة شخصًا واحدًا عند عد الطعام |
| RSVPSubmission | رد منطقي وإجابات وإصدار سياسة | عملية شراء أو حالة delivery |
| MealAllocation | عدد أشخاص لكل mealOption داخل رد | سعر أو طلب مطعم مؤكد |
| DietaryAnswer | قيود قالها الضيف ومَن تخصه إن عُرف | تشخيص أو ضمان استيفاء |
| GiftItem | رغبة وصورة ورابط معلن | إثبات شراء |
| OutboundAttempt، لاحقًا للمزود | محاولة إرسال وحالتها ومصدرها | دمج فتح واتساب مع confirmed RSVP |
| PaymentAttempt، فقط عند التكامل | معاملة وحالة receipt من provider | الاستنتاج من query string في return URL |

## واجهات مقترحة

```ts
// Contract sketch only; not a runtime implementation.
type GuestExperiencePolicy = {
  revision: number;
  meals: {
    enabled: boolean;
    required: boolean;
    options: Array<{ id: string; label: string; archived: boolean }>;
  };
  dietary: { enabled: boolean; prompt: string };
  gifts: { enabled: boolean; showAfterDecline: boolean; itemIds: string[] };
};

type GuestAnswerInput = {
  expectedExperienceRevision: number;
  idempotencyKey: string;
  attending: boolean;
  count: number;
  meals?: Array<{ optionId: string; count: number }>;
  dietary?: {
    answered: boolean;
    categories: string[];
    affectedCount?: number;
    personLabel?: string; // optional: guest/companion name or seating reference
    note?: string;
  };
  note?: string;
};
```

لا نرمي هذه المعلومات في `guestNote` ثم نحاول استخراج totals من النص. يظل note الحر متاحًا، لكن الوجبة والكمية لهما حقول وقواعد واضحة. لا تتحول categories إلى قائمة طبية شاملة؛ اختيارات بسيطة قابلة للفهم ونص اختياري عند الحاجة.

## ثوابت العدد

1. كل optionId ينتمي إلى نفس event والسياسة المنشورة التي رد عليها الضيف، ولا يوجد option مكرر في payload.
2. الكميات أعداد صحيحة غير سالبة، وcount بين 1 وmaxGuests عند القبول.
3. إذا كانت الوجبة مطلوبة: مجموع quantities = count. إذا كانت اختيارية: المجموع ≤ count، والفرق «لم يحدد وجبة» ويظهر في التقرير.
4. مثال 4 أشخاص: 2+1+1 صحيح؛ 4+4 مرفوض. لا تضرب اختيارًا واحدًا في عدد العائلة دون فعل واضح من المستخدم.
5. عند الاعتذار: count=0، لا تخصيص طعام نشط. القيود السابقة لا تبقى محسوبة في confirmed totals.
6. عدد أصحاب القيود، إذا أُدخل، بين 1 وcount؛ unknown عدد مجهول لا صفر.
7. اختلاف العائلتين في الاسم لا يثبت هويتين منفصلتين، وتشابه الاسم لا يبرر دمجهما تلقائيًا.

## النشر وإصدارات الأسئلة

**المقترح:** إعداد تجربة الضيف له draft/revision وpublished snapshot، وينشر مع التصميم في عملية واحدة. لا تُكرر حقول الموعد والمكان داخل التصميم لتطبيق ذلك؛ هذه لها عقدها الحالي المختلف.

`publishInvitation(eventId, expectedDesignRevision, expectedExperienceRevision)` يأخذ snapshot متسقًا؛ إذا عُدلت مسودة من تبويب آخر يرجع conflict مفهوم. يظهر للمضيف ملخص: «القالب + خيارات الطعام + رابط الهدية» ثم نشر واحد. الحفظ التلقائي ليس نشرًا.

الضيف يستلم `experienceRevision`. إذا حذف المضيف خيار أسماك أثناء أن الضيف يرد، لا نبدله صامتًا بلحوم: conflict يعيد أحدث سياسة ويحفظ العدد والملاحظات والاختيارات التي ما زالت صالحة، ثم يطلب مراجعة البند المتغير.

بعد وجود إجابات، تُؤرشف options القديمة بدل محو IDs أو إعادة استخدامها. لا تغير تسمية وجبة تاريخية على نحو يجعل الرد القديم يعني شيئًا جديدًا. إضافة سؤال جديد لا تعني أن من رد سابقًا أجاب «لا» عليه، ولا تُرسل تذكيرات آليًا دون فعل واضح من المنظم.

## RSVP والحفظ الصادق

تكون الحالة `editing → submitting → success | error`. لا تُطلق نهاية pack/seal/fly باعتبارها نجاحًا قبل receipt ناجح. يمكن حركة انتظار أثناء الشبكة، لكن النجاح يأتي من العقد.

عملية الرد تكتب الحضور والأعداد والطعام والقيود في transaction واحدة. `idempotencyKey` نفسه مع payload نفسه يعيد النتيجة الأصلية عند retry؛ payload مختلف يحتاج مفتاحًا جديدًا، أو يرجع conflict بدل تنفيذ غير واضح. لا يُستخدم timestamp وحده لمنع التكرار.

تعديل رد شخصي يحدّث الإجابة النشطة ويضيف activity مختصرًا، لا يُجمع مع الرد السابق كأنه ضيف إضافي. عند فقد الشبكة بعد وصول الطلب، retry لا يكرر الرد. إذا أُغلقت نافذة الرد، يظهر السبب ويحافظ النموذج على ما كتبه دون وعد بالحفظ.

## الرابط العام والمطابقة

الإجابات قبل المطابقة تظل تحت responseId. dashboard يميز «مؤكدون من الدعوات» و«ردود عامة تنتظر المطابقة»، ويعرض الرد العام حتى مع صفر parties. لا تُجمع totals غير المطابقة مع canonical counts دون تسمية واضحة.

عند match/add: ينتقل المرجع أو يحل إلى party واحدة؛ لا يُنسخ الرد ليُعد مرتين. إذا كانت العائلة لديها إجابة مختلفة، تُعرض مقارنة ويختار المنظم النسخة المعتمدة. تعديل الرد العام يحتاج token تعديل opaque خاصًا بالرد عند اختيار دعم هذه الوظيفة؛ لا يكتفي بالاسم. ينشأ من الخادم، يُخزن hash فقط، لا يظهر في logs أو analytics، وله حدود إتاحة واضحة.

لا نضيف رقم الهاتف إجباريًا للضيف العام لمجرد تسهيل المطابقة؛ القرار يعتمد على حاجة فعلية. الرابط الشخصي يظل الطريق الأدق عند رغبة المنظم في سماحيات عائلية وهوية معروفة.

## التقارير: مصدر واحد للأعداد

| التقرير | الأساس | حالات يجب إظهارها |
| --- | --- | --- |
| الحضور | آخر إجابة canonical لكل party | مؤكد/معتذر/لم يرد؛ الأشخاص مختلفون عن الدعوات |
| الوجبات | التخصيص النشط للحاضرين | غير المحدد، إجابات قديمة تحتاج مراجعة، provisional unmatched منفصل |
| الطاولة | party الحالية ومجموع confirmedPartySize | زيادة سعة، عائلة معتذرة ما زالت موزعة، غير موزعين |
| الطعام لكل طاولة | join على نفس party/allocation | نقل party يعيد تجميع الطعام دون نسخ أو حذف الإجابة |
| قيود الطعام | answered flag + المحتوى | «لم يُجب» مختلف عن «أجاب بلا قيود» |
| تصدير | نفس query/selector الذي يغذي الشاشة | timestamp وrevision وإجماليات تطابق الشاشة |

لا نخزن counter يدويًا في 4 شاشات. المشتقات تُحسب من نفس snapshot أو read model. مع تحديثين متزامنين يجب إبطال cache لكل الشاشة المعنية. عند كبر القوائم، pagination/filter على الخادم والتصدير يشمل المجموعة المطلوبة لا الصفحة المرئية فقط.

## WhatsApp: ثلاثة أنواع أدلة لا تختلط

| الدليل | ما يمكن قوله | ما لا يمكن قوله |
| --- | --- | --- |
| فتح wa.me | فُتحت محادثة/بدأت المشاركة | وصل/قرأ/أرسل تلقائيًا |
| فعل المنظم «تم التواصل» | تم تحديده يدويًا، source=manual | receipt من المزود |
| webhook موثوق من provider | الحالة التي أكدها المزود | قراءة محتوى رد الضيف إذا لم تصل خدمة لذلك |

حالة `opened` للدعوة تعني أن رابط الدعوة فُتح، وليست بالضرورة read receipt لرسالة واتساب. يجب فصل timeline الرابط عن محاولة الرسالة حتى إذا اختُصرتا بصريًا.

عند إرسال حقيقي: job/attempt لكل مستلم ومفتاح ثابت لكل محاولة مقصودة، partial failure، retries لا تعيد إرسال الناجح، dedup للwebhooks، وتطبيق الحالة بترتيبها المنطقي لا حسب وصول webhook آخر. تعارض read/delivered أو فقد callback لا يتحول إلى success مصنوع. هذا نطاق provider مستقل عن polish قائمة الضيوف.

## الهدايا وطبقة الدفع الاختيارية

في external-link mode: GiftItem له عنوان وصورة ووصف ورابط https مع label واضح؛ لا PaymentAttempt ولا رصيد ولا counter نقدي. URLs تُفحص، ولا يُقبل javascript/data URL أو HTML يضيفه المنظم. لا تجلب preview من أي عنوان داخلي عشوائي على الخادم.

إن اختير الدفع المتتبع لاحقًا: معاملة منفصلة عن RSVP، مبلغ صحيح بوحدة العملة الصغرى، عملة وrecipientId ومزود، server-created reference، receipt مؤكد، idempotency وwebhook signature. return URL من المتصفح لا يغير paid flag. refund/cancel/expiry وعدم توافق العملة حالات تصميم وتشغيل حقيقية تحتاج تعريفًا قبل تفعيل التكامل.

لا نختار بلدًا أو فوري أو محفظة داخلية لكل العملاء لأن المراجع ضرب مثالًا بها. ولا يُحجز gift inventory أو يختفي item تلقائيًا لمجرد ضغط الرابط. حجز رغبة غير مالية إن اختير مستقبلًا يحتاج تنافسًا ذريًا وحالة تحرير/انتهاء مستقلة، وهو ليس جزء external-link MVP.

## الوصول والخصوصية المرتبطان بالميزات المطلوبة

الضيف يرى دعوته وإجابته فقط؛ لا هواتف غيره أو قيود طعامهم أو مبالغهم. المنسق يرى ما يلزم مهمته، وتقرير الطعام يمكن أن يقتصر على الطاولات والأعداد والقيود اللازمة دون الهواتف والهدايا. لا نُصدر diet notes افتراضيًا إلى analytics أو CSV عام بلا اختيار.

أي جدول جديد في schema مكشوفة يحتاج grants وRLS متوافقين مع عضوية المناسبة، مع اختبار allow وdeny؛ view للتقارير يجب أن يحترم نفس الوصول. تُراجع RPCs المجهزة التي تستخدم SECURITY DEFINER وsearch_path وexecute grants قبل ربطها، ولا تُنسخ كحل تلقائي لكل منع وصول.

لا تُرسل service credentials إلى الواجهة. runtime errors تسجل code/correlationId، لا payload الأسماء والهواتف والقيود وروابط التعديل. يُعرّف عمر الاحتفاظ/الحذف عند إعداد خدمة حقيقية؛ البيانات التشغيلية للطعام لا تحتاج البقاء إلى الأبد بعد إغلاق المناسبة.

## خطة تغيير آمنة

إضافة جداول/حقول اختيارية وعقود جديدة مع بقاء العملاء القدامى، وdefault للميزات القديمة = off. لا تُحول guestNote القديمة تلقائيًا إلى allergy. migration + remote mapper + mock + fixtures + read models تتغير في دفعة متوافقة، ثم تُفعل الميزة. عند rollback يُوقف toggle الظهور دون حذف الإجابات المكتوبة.
