# UX & product decisions (reversible assumptions)

Spec §36: when a detail was not decided, the simplest reversible MVP behaviour was chosen and recorded here. Each entry says what to change if testing proves it wrong.

| # | Decision | Why | Reverse by |
|---|---|---|---|
| D-001 | **React 19 + TypeScript SPA** (esbuild), not Next.js, for this prototype. Route paths mirror the spec IA 1:1. | Next.js can't be installed in the build sandbox (registry blocked), and the prototype must also run as a static page for phone usability tests. Domain, services and features are framework-agnostic or plain React. | Move each route in `src/app/App.tsx` to `app/<same path>/page.tsx`; keep `domain/`, `services/`, `features/`, `ui/` as they are. |
| D-002 | **InvitationParty** is the unit of guest management (one invitation = a person, couple or family, with an allowed size). | Spec §12. No household CRM, no global guest identity. | Add a `Person` entity under parties later; parties stay the RSVP/check-in unit. |
| D-003 | **Event data vs invitation data.** Date, time, time zone and venue live only on the Event and are read-only inside the designer, with a link to settings. Names on the card are invitation-level overrides: blank or equal to the event's names means "use the event's names". | Spec §10: "invitation edits must not overwrite event data". The organizer always sees which is which. | Make the names read-only too, or let the designer edit event data with an explicit "this changes the event" notice. |
| D-004 | **Western digits and the Gregorian calendar** in the organizer UI. Arabic month names; Arabic plural rules via `Intl.PluralRules('ar')`. | Phone numbers, counts and tables are easier to compare and type. Saudi and Egyptian apps commonly do the same. | `src/domain/format.ts`: change the locale string `ar-u-ca-gregory-nu-latn`. |
| D-005 | **Saudi Arabia is the default country** for local phone numbers (05…). Egypt (01…) and the GCC are recognised by their prefixes. Arabic-Indic digits and Excel number formats are normalised. | Most likely early market; matches the seed data. | `defaultCc` in `src/domain/phone.ts`, or an event/account setting. |
| D-006 | **Draft and published invitation versions.** Every edit autosaves to the draft. Guests see the last published snapshot until the organizer publishes again. "Unpublished changes" is a visible state. | Spec §10: the organizer must always know "is this saved? is this published? what will guests see?". | Publish on every save (remove the snapshot) if testers find two states confusing. |
| D-007 | **Delivery state is separate from RSVP state**, and every delivery state says who knows it: the platform (opened), the organizer ("contacted manually" / shared via WhatsApp), or a simulation (automatic send). `draft` and `ready` are derived from the publish state, not stored. | Spec §13, §15. | — |
| D-008 | **WhatsApp:** "share via WhatsApp" opens a real `wa.me` link with a prepared message and marks the invitation shared (manual). "Automatic send" and reminders are clearly labelled simulations: they fail for missing phone numbers so the failed and retry states can be tested. | No BSP integration in this phase (spec §25). | Implement `PartyRepository.simulateSend` on the backend with a real provider; the UI states already exist. |
| D-009 | **Declining never removes a table automatically.** The seating page flags "declined but still seated" with a one-tap fix. Over-capacity seating is allowed only after an explicit confirmation. | Spec §15 ("cleared or flagged"), spec §16 warnings, and "show, don't silently fix". | Clear `tableId` in `applyRsvp` if organizers prefer it. |
| D-010 | **QR scanning is simulated** in gate mode: staff type or paste the code or link, or pick a test case (confirmed, partial, already used, declined, not replied, no table, unknown code). The QR shown to guests is real and encodes their personal link. | Spec §17 allows a browser simulation. Real camera scanning needs permissions and HTTPS on devices. | Add `BarcodeDetector` / camera capture to `ScanSimulator`; `codeFromScan` already parses real payloads. |
| D-011 | **Gate mode works before the event day.** It shows a banner saying any check-in counts and can be undone. Every check-in can be undone from the confirmation screen. | Lets organizers rehearse ("جهز الدخول") and testers run tests 6–7 any day. | Lock gate mode to event day ± hours. |
| D-012 | **Partial check-in:** staff choose "how many are entering now". The counter starts at the remaining expected count. Exceptions (declined, not replied, more than confirmed, more than allowed, already complete) need a checkbox ("I confirmed with the organizer") and an optional note, and are listed for the organizer to review. "No table" is shown but doesn't block. | Spec §17: "do not silently fix exceptions". | `BLOCKING` set in `src/domain/checkin.ts`. |
| D-013 | **General (unnamed) link** is off by default. When on, replies arrive as "needs matching" items: match to a party, add as a new guest, or dismiss. The seeded wedding has it on, with two waiting replies. | Real-world WhatsApp groups. Keeps the guest list the source of truth. | Toggle in event settings. |
| D-014 | **Guests can change their reply until the event starts.** Companion names and a note are optional and asked in the event hub, not in the cinematic RSVP page, which keeps its canonical three fields. | Spec §14: "do not ask too many questions"; preserves the Invitation Studio. | Add fields to the RSVP page in `src/pages/index.js`. |
| D-015 | **Mock persistence = browser storage**, one store behind the repository interfaces. Same-browser tabs sync live (a guest RSVP in another tab updates the organizer immediately). Other devices don't share data. | Spec §3: no backend in this phase. | Implement `services/contracts.ts` against the NestJS API in `services/index.ts`. |
| D-016 | **Seed data is relative to today.** The wedding is always 9 days away ("before" scenario) or today ("event day" scenario, with arrivals already recorded). The completed event was 20 days ago. Prototype tools switch scenarios and reset data between testers. | Tests must behave the same on any day. | `src/services/mock/seed.ts`. |
| D-017 | **Roles are mocked.** Organizer and coordinator differ only in that archiving the event is organizer-only. | Spec §6: no permission builder. | `SessionService` + checks in features. |
| D-018 | **Mobile tab bar:** نظرة عامة · الدعوة · الضيوف · الجلوس · المزيد (الردود، الدخول، الإعدادات، الملخص). Reply follow-up is also reachable from the overview and the guest filters ("لم يرد بعد"). | Five tabs fit a phone; invitation and guests are the most frequent tasks before the event day. | `mobile` array in `src/features/workspace/EventWorkspace.tsx`. Re-test after round 1 whether الردود deserves a tab. |
| D-019 | **Invitation designs assume two names** (couple events). Other event types can be created and managed fully; their invitation shows the names typed in the two name lines. | The Invitation Studio's 10 cards are couple designs; redesigning them is out of scope (spec §2). | New card templates per event type. |
| D-020 | **Short guest links** `/i/<slug>/<CODE>`. The slug comes from the English names, else a short code; the 5-character code avoids look-alike characters so it can be read aloud at the gate. | Spec §10. | `src/domain/ids.ts`. |
| D-021 | **The organizer UI theme is replaceable.** Raw colours exist only in `src/ui/styles/tokens.css`, including two re-themes: `.theme-guest` (guest hub, invitation-flavoured) and `.theme-gate` (dark, high-contrast check-in). The invitation keeps its own cinematic styles. | Spec §4, §26. | Edit tokens and primitives; features need no change. |
| D-022 | **On phones, the designer's live preview runs only while the Preview sheet is open.** It is freed when the sheet closes or the step changes. Desktop keeps the side-by-side live preview. | Usability round 0: a hidden 3D scene kept rendering behind the form, making typing sluggish on weaker phones. | `_wantPreview()` in `src/wizard/Wizard.js`. |
| D-023 | **Arabic counts use the grammatical case.** After a verb, a preposition or a construct noun, counts use the oblique dual («تسجيل دخول شخصين», «من دعوتين»); standalone counts stay nominative («شخصان»). | Usability round 0: «تسجيل دخول شخصان» reads as an error to Arabic speakers. | `pluralOf` / `peopleOf` versus `plural` / `people` in `src/domain/format.ts`. |
| D-024 | **Destructive confirmations start on «تراجع».** Delete and reset dialogs focus the safe button; other confirmations focus the main action. | A stray Enter must never delete guests or reset data. | `ConfirmDialog` in `src/ui/primitives/Overlay.tsx`. |
| D-025 | **The platform invitation editor replaces the 5-step wizard** at `…/invitation/design`. It drives the Studio engine directly for the live preview. The standalone wizard (`?view=wizard`) is unchanged and keeps its QA. D-022 now applies to the standalone wizard only. | UI/UX brief §11: free section editing instead of a forced order; the owner wants the editor. | Route `invitation/design` back to `InvitationDesigner` (kept in the repo). |
| D-026 | **Event details are editable inside the editor** (date, time, venue, map, party size) with an explicit «هذه بيانات المناسبة نفسها» notice and a separate save. The preview shows unsaved edits instantly. This supersedes D-003's "read-only in the designer"; names on the card remain invitation-level overrides. | Owner test task 4 ("change names, date and style, then view as guest") in one place. | Make `EventSection` read-only with a link to settings. |
| D-027 | **Templates are curated presets** (13) over card × setting × experience, using only pairings the engine recommends. Applying a preset changes the look only, never texts. | UI/UX brief §9: no flat grid of 100 combinations. | `src/domain/templates.ts`. |
| D-028 | **Occasion catalogue: 13 types in 5 groups**, one list shared by every chooser (popular first). New types (مولود، إفطار رمضان، مؤتمر، افتتاح، مناسبة شركة) use the existing couple-oriented invitation designs (see D-019). | UI/UX brief §7. | `EVENT_TYPES` in `src/domain/event.ts`. |
| D-029 | **UI fonts are self-hosted open stand-ins** (Readex Pro display, IBM Plex Sans Arabic UI), because the brand's Shinko Sans / Ping AR + LT are not licensed for the prototype. | Master prompt §3: no fake or unverified hot-linked brand fonts. | Swap files in `public/assets/fonts/` and `--font-*` tokens. |
| D-030 | **Creating an event ends in the template gallery**, not the overview. «سأختار لاحقًا» goes to the overview. | Emotional momentum; time to first value. | `navigate(paths.overview(...))` in `CreateEvent`. |


## Final polish decisions — 10 October 2026

| # | Decision | Why / reversal |
|---|---|---|
| D-031 | Opening WhatsApp never marks delivery. Explicit “نعم، أرسلته” or manual contact does. **Supersedes D-008.** | Canceling a composer must not falsify delivery; change only when a real provider reports delivery. |
| D-032 | Direct catalogue is default; Coverflow and Rail remain optional. | All 13 occasions discoverable; switch in reviewer options. |
| D-033 | Adaptive grouped navigation; replies are a view beside guests; phone tables becomes reception on event day. **Supersedes D-018.** | Supports the current task without losing routes. |
| D-034 | Invitation-first home and event-first overview, with three relevant facts and top-three ranked attention. | Keeps the primary next action visible; all exceptions remain expandable. |
| D-035 | DraftQueue serializes and coalesces saves. | Prevents slow old saves overwriting newer edits; retain if backend replaces mock repository. |
| D-036 | Invitation fonts are self-hosted Amiri, Aref Ruqaa, Cormorant Garamond, Great Vibes and Reem Kufi; UI faces unchanged. | Offline/network resilience and deliberate local fallback; licenses included. |
| D-037 | Six initial templates, lazy still posters, bounded face cache. | Fast choice while all 13 presets remain available. |
| D-038 | Guest has direct date/RSVP shortcut independent of cinema. | Invitation failures do not block the practical response journey. |
| D-039 | Arrival summaries subtract checked-in people from confirmed people per party. | One family member arriving does not mean the whole family arrived. |
| D-040 | Prototype controls hidden by default, exposed in review or offline recovery. | Keep normal product flow clear while preserving test tools. |

## «توقيع» signature pass — 10 October 2026

| # | Decision | Why / reversal |
|---|---|---|
| D-041 | **«توقيع» is a mix of three modes.** A «احتفال» (red) for entry, C «تحرير» (white, colour tiles) for data screens, B «مساء» (charcoal/gold) for guest and reception moments. | Owner chose «مزيج» after rejecting the beige identity pass for weak contrast. See `review/STYLE_DOSSIERS.md`. |
| D-042 | **No generated imagery and no hand-drawn icons in «توقيع».** Icons are Phosphor 2.1.1 (MIT), vendored. Occasion visuals are a glyph on a brand tile plus a real rendered invitation. | Owner instruction. Checked by `tests/dev/signature-no-generated.mjs`. Other themes keep their art for comparison. |
| D-043 | **The brand font Ping AR + LT is used for organizer headings in the local prototype only**, with the owner's permission. Readex Pro is the fallback in the stack. **Supersedes D-029 for «توقيع» only.** | It is a desktop licence; a web licence is needed before deployment (`assets/asset-briefs.json` `signature.identity.fonts.v1`). Invitation faces stay on OFL fonts. |
| D-044 | **Creating an event opens the prepared invitation in the editor** (`…/invitation/design?first=1`) with the occasion starter. The template gallery is optional. **Supersedes D-030.** | Fewer decisions before the first useful result. |
| D-045 | **Text contrast pairs are fixed:** white on red, charcoal on gold, charcoal on turquoise, gold on charcoal. Gold and turquoise are never text on white; white is never text on gold or turquoise. | Measured: 5.1 / 6.5 / 6.2 / 6.5 versus 2.3 / 2.5. |
| D-046 | **RTL "next" is leftward everywhere:** swipe left, ArrowLeft, the «التالية» button and trackpad. Flings move at most 3 cards. | `review/GESTURE_SPEC.md`. |
| D-047 | **The phone editor sheet has three stops (peek / half / full) and no closed state.** | A gesture can never hide unsaved edits. |
| D-048 | **Guest and import copy is occasion-neutral** («الأهل، الأصدقاء، زملاء العمل»). | Wedding-only side labels leaked into single-person events. |
